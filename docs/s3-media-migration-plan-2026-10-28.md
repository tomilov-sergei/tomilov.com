# План переноса медиа tomilov.com в существующее S3

Дата: 28 октября 2026. Статус: обследование и предложение; production не изменён, перенос и удаление не запускались.
Исходный чат: «Разбор и очистка места на сервере Timeweb», 01a182b2-7ca9-7220-9e5c-fa0d209bcd8b.

## Решение и границы

Использовать существующий S3, уже обслуживающий `/assets/telegram/live/`. Перенести исторические бинарные файлы Telegram, затем оригиналы и производные личных фото. Оставить публичные URL на tomilov.com прежними через nginx reverse proxy. `posts.json` и `photos.json` оставить на production shared storage как оперативные источники истины, с отдельными резервными копиями. После приёмки S3 становится источником истины для перенесённых бинарных объектов — это требует дополнения ADR 0002 и правил фото, а не молчаливого изменения политики.

Не переносить весь shared каталог одним рекурсивным upload: в нём есть другие данные. Downloader, Collector, его синхронизация, релизы, appcast и nginx-правила Collector вне задачи. Barcelona Guide и прочие статические ресурсы оставить для отдельной инвентаризации: они не нужны для основного освобождения места. Новых ресурсов не покупать, диск и тариф не расширять.

### Существующее S3: факты и неизвестное

- Фактический nginx upstream: `https://s3.twcstorage.ru/00df5bd5-137f-492a-8d95-c7ee2cc2d851/assets/telegram/live/`.
- Endpoint и bucket подтверждены текущей nginx-конфигурацией и публичным чтением объекта. Это идентификаторы ресурса, не ключи доступа.
- `ru-1` задан как default в действующем коде; фактический signing region из env ещё не подтверждён.
- В production posts.json найдено 188 различных live src, включая 44 видео. Это число ссылок, НЕ полный список объектов бакета.
- Один live JPEG проверен напрямую в S3 и через сайт: HEAD 200, GET Range 206, ожидаемые размер и Content-Type.
- Один live MP4 через сайт: HEAD 200, `video/mp4`, начальный и суффиксный Range по 32 байта — 206 с корректным Content-Range. Это выборочная проверка, не приёмка архива.
- Анонимные ListObjectsV2 и GetBucketLocation возвращают 403. Это не означает, что бакет пуст или неисправен.
- `/etc/tomilov-telegram-live.env` и `/etc/tomilov-photo-upload.env` недоступны deploy-пользователю. Подключённой браузерной сессии Timeweb не обнаружено. S3 credential, authenticated list, versioning, lifecycle, multipart, реальный тариф, занятый объём и остаток 100 ГБ не проверены.
- 100 ГБ — заявленный пользователем оплаченный объём; нельзя считать его свободным. Перед стартом получить сведения панели плюс полный paginated inventory, включая версии/delete markers и незавершённые multipart, если включены. Сумма текущих объектов не всегда равна тарифицируемому объёму.
- На Mac urllib столкнулся с ошибкой доверия TLS; повторная проверка с VPS прошла с проверкой сертификата. `--insecure` не использовать.

## URL, доступ и выдача

Ключ равен прежнему URL без ведущего `/`, например `assets/telegram/video_files/...`. Сохранять регистр, Unicode и корректное percent-encoding без двойного кодирования. До записи сравнить пересечения с уже существующим S3: одинаковый key с другим SHA-256 — конфликт и остановка, не overwrite.

Рекомендуемый начальный режим — публичный GetObject только для уже публичных медиа сайта, закрытый List и Write, по возможности policy по точным prefixes. Не включать public-read всему бакету. Проверить содержимое `files`: если обнаружатся непубличные объекты, исключить их из публичной policy и согласовать приватную выдачу. Мигратору нужны scoped List/Get/Put, multipart ListParts/Abort; удаление целевых объектов не нужно. Prune удаляет только локальные пути из принятого manifest. Отдельные runtime credentials по prefixes, без Delete. Если требуется закрытый origin, нужен подписывающий proxy/gateway; обычный nginx proxy не умеет сам подписывать S3 SigV4, а постоянные presigned URL в HTML не подходят. Этот вариант не считать уже реализованным.

Reverse proxy сохраняет same-origin, SEO, RSS и внешние ссылки без массового переписывания JSON. Передавать Range/If-Range, conditional headers; HEAD не заменять GET. Проверять 200/206/304/404/416, Content-Length/Content-Range, seek начала/середины/конца MP4, MIME для каждого типа. Не превращать ошибки origin в HTML 200. TLS/SNI и проверка сертификата обязательны. На этапе миграции без proxy_cache; `proxy_max_temp_file_size 0` или отключённая buffering для больших медиа, чтобы nginx не складывал видео на почти полный диск. Настроить ограниченные timeouts; не менять upload-body buffering без отдельной проверки.

Для уникальных неизменяемых ключей Cache-Control public, max-age=2592000, immutable; при замене содержимого выдавать новый ключ. Для mutable manifests короткий кеш/ревалидация и никакого immutable. Проверить фактические заголовки без дублей. CORS для same-origin не требуется; если позже будет прямой домен S3, отдельно проверить CORS, CSP, canvas и Range. CDN в эту миграцию не включать.

## Этапы и критерии перехода

1. **Доступ и preflight.** Владелец/оператор предоставляет безопасный запуск от service identity либо отдельный scoped credential через закрытый env-файл, а также доступ к сведениям тарифа/трафика. Для nginx/systemd нужен администратор или узко разрешённая операция, не полный passwordless sudo. Установить bucket/region/endpoint, usage, versioning, lifecycle и автоапгрейд. Получить запас >= объём отсутствующих объектов + ограниченные multipart + прогноз роста; предварительный порог запаса 15 ГиБ. Если оплаченный предел нельзя гарантировать — остановка до загрузки. Тестовые Put/Get/HEAD/multipart/abort выполнять только после начала реализации в отдельном согласованном prefix, не во время этого обследования.
2. **Реализация и изолированная проверка.** Отдельный чистый checkout/ветка, сохранить нынешнее грязное дерево. Выполнить перечисленные изменения и тесты, git commit/push до production по правилам проекта. Подготовить точный diff nginx/systemd и команды проверки, rollback конфигурации. Проверить полный обычный deploy и PHOTOS_ONLY без дисковых originals в тестовой среде.
3. **Инвентаризация источника.** Потоковый SHA-256 всех 2339 исторических файлов Telegram и 443 бинарных фото; фиксировать relative path, size, mtime_ns, device/inode, MIME, SHA-256, целевой key. Зафиксировать отдельно два manifests и список их ссылок (включая rich media), generated HTML/canvas/RSS. Сверить orphan/missing, не удалять orphan по предположению. Все старые оригиналы сохраняются. Manifest/журнал держать вне публичного web-root и дополнительно на рабочей машине; внутри не должно быть Telegram API token-paths.
4. **Копирование без локального дубля.** VPS читает исходники напрямую, multipart по 32–64 МиБ, старт с 2 worker и общим лимитом 5 МиБ/с; не более 4 одновременно буферизуемых частей, контролировать RAM. Перенос 10,37 ГиБ при 5 МиБ/с занимает теоретически около 35 минут, без хеширования, проверок и повторов. Это не SLA. Если RAM/latency недостаточны, уменьшить concurrency. Никаких tar/rsync staging. При рестарте продолжить uploadId/parts из журнала, перепроверить источник; skip допустим только по подтверждённому size+SHA-256. Сохранять completed/verified как разные состояния. Убирать только принадлежащие запуску устаревшие multipart; чужие не затрагивать.
5. **Полная проверка.** SHA-256 локального потока сравнить с SHA-256 полного GET из S3 для каждого объекта, GET сразу хешировать и отбрасывать, без файла-копии. HEAD проверяет size/type, но не доказывает байтовую идентичность. ETag multipart не считать MD5; метаданные sha256, записанные самим uploader, сами по себе не доказывают целостность чтения. Проверить завершение multipart и возможность прочитать объект. Фиксировать retries/ошибки; любой mismatch запрещает prune. Перед переключением повторно проверить размеры/mtime и дозалить дельту.
6. **Переключение записи и выдачи.** Запретить конкурирующие deploy/ручные импорты, кратко остановить приём фото с явным retryable ответом; Telegram события должны надёжно оставаться в outbox либо повторяться Telegram — доказать это тестом до паузы. Сначала установить совместимый S3 reader/proxy для ещё не опубликованных новых путей, затем переключить writer, дренировать очередь и сверить финальную дельту. Старый архив всё ещё локален. Для старых media nginx переключить на S3 canary location/набор, затем все approved prefixes после `nginx -t`. Не делать временные permanent redirects. Все конфиги сохраняются для быстрого возврата.
7. **Приёмка сайта.** Все 2782 локальных бинарных файла совпадают по размеру и SHA-256 либо каждая разница разобрана; полный authenticated S3 inventory и live-объекты проверены отдельно. Все ссылки из актуальных manifests доступны. Репрезентативные desktop/mobile проверки: главная, overlay, RU/EN screenshots, фото SDR/HDR, feeds, скачать файл, seek видео. Новое фото и live-пост публикуются через штатный вход, переживают retry/restart и deploy, локальный архив не растёт. Проверить 404 и неправильный Range, не только успешные запросы. Счётчики ошибок/очереди и latency не хуже согласованного baseline. Синтетические данные не публиковать в реальном канале без разрешения.
8. **Выдержка и удаление.** Предлагается 24–48 часов наблюдения при сохранённых локальных originals, но длительность ограничена текущими 979 МиБ: заранее остановить неограниченные локальные записи, держать alert на 512 МиБ и abort миграционных записей при 256 МиБ. Не ускорять удаление в обход доказательств. Показать отдельный deletion report с конкретным manifest digest, числами/байтами и актом приёмки. После разрешённого удаления удалять только verified regular files из allowlist, проверив path containment, symlink и текущий stat/hash. Сначала видео как основной выигрыш. Два JSON, outbox, manifests и другие shared каталоги не удаляются. Проверить df и нулевое восстановление originals следующим deploy.

## Откат и сохранность

До удаления: вернуть старые location для исторических объектов, сохранив S3 location для новых объектов. Вернуть совместимый reader/writer релиз; не откатывать manifests к старому snapshot и не терять новые записи. Фото, созданные уже в S3, не существуют локально, поэтому старый photo writer/generator без S3-совместимости не является безопасным rollback. Минимальная версия rollback должна уже уметь оба storage backend.

После удаления: простой rollback nginx на локальные файлы невозможен. Можно откатить приложение, оставив S3-выдачу; полное восстановление локальных оригиналов требует обратного скачивания и достаточного места. Это отдельная операция, не обещание мгновенного отката. До prune проверить независимую восстановимость архива: сопоставить существующую копию на рабочей машине по manifest или сделать внешнюю резервную копию вне почти полного VPS. Непроверенный локальный mirror не считать бэкапом. Если независимой копии нет и делать её некуда в имеющихся ресурсах, удаление отложить; новый платный ресурс не создавать. Versioning в том же бакете может помочь от случайного overwrite, но не является независимым бэкапом и потребляет квоту.

## Расходы и наблюдаемость

Оплаченные 100 ГБ хранения не означают безлимитную раздачу. Официальная документация Timeweb сообщает общий бесплатный исходящий лимит 100 ГБ/месяц (1000 для Prime) и возможность ограничения трафика; применимый класс, цену сверх лимита и текущий расход надо подтвердить в аккаунте. Полный GET для верификации добавит около 11,13 десятичных ГБ исходящего трафика S3; независимое скачивание ещё столько же. При двух полных чтениях резервировать около 22,3 ГБ плюс live-объекты и обычный трафик сайта. Proxy сохраняет расход S3 и VPS, он не делает трафик бесплатным.

Не включать автоапгрейд. Если он уже включён — зафиксировать состояние и согласовать его отключение оператором; собственный preflight и stop-limit не заменяют ограничения провайдера. Не включать жёсткий лимит трафика без понимания последствий: исчерпание может отключить раздачу сайта. Сначала алерты на 70/85/95% подтверждённых квот, прогноз роста и бюджет, затем согласованный hard cap. Проверять версии и незавершённые parts в usage.

Метрики: VPS free bytes/inodes, объём managed tmp, Bot API cache, upload bytes/ошибки/retries, pending/oldest outbox, verify mismatch, незавершённые multipart, S3 usage/egress, nginx upstream status/latency и 4xx/5xx по media prefixes. Логи с ротацией, без Authorization, подписанных query и Telegram token paths. На время переноса — регулярный ограниченный отчёт прогресса, затем проверки доступности HEAD/малого Range и тревоги на изменения; полное ежедневное перечитывание 10 ГиБ не нужно. Автоматизации сейчас не создавались.

Источники тарифных условий (проверены 28.10.2026):
- https://timeweb.cloud/docs/s3-storage/tariffication
- https://timeweb.cloud/docs/s3-storage/manage-storage/s3-autoscaling
- https://github.com/timeweb-cloud/s3-examples

## Понятная точка запуска

Следующий разрешаемый шаг: реализация и тестирование описанных изменений, плюс закрытие preflight доступа/квоты. Production migration стартует отдельной командой нового инструмента только после принятия плана и успешных preflight/test gates. Предлагаемый интерфейс (инструмент пока НЕ создан):

```text
migrate_media_to_s3.py inventory --config <private-config> --run <id>
migrate_media_to_s3.py copy      --config <private-config> --run <id>
migrate_media_to_s3.py verify    --config <private-config> --run <id>
migrate_media_to_s3.py report    --run <id>
# затем отдельные проверенные операции cutover nginx/writers
# prune отдельно, только по принятому manifest и после выдержки
```

Для начала реализации достаточно одобрения плана; для production потребуются подтверждённые bucket usage/region/права и оператор nginx/systemd. Секреты в чат передавать не нужно. Текущий документ не подтверждает эти отсутствующие доступы и не разрешает сам по себе production cutover или удаление.
